# Workflow: Code Review

## 1. Objective

Define a structured process for reviewing code changes before they are considered ready for integration.

The objective is to evaluate correctness, security, maintainability, architecture and potential regressions.

A code review must identify actionable problems supported by evidence, not merely express stylistic preferences.

## 2. When to Use

Use this workflow when:

- Reviewing a Pull Request.
- Reviewing a branch before merging.
- Analyzing recent commits.
- Evaluating code generated by an AI agent.
- Reviewing a new feature.
- Checking bug fixes.
- Auditing modifications to critical modules.
- Verifying code quality before delivery.

## 3. Execution Process

### Phase 1 — Understand the Change

Before reviewing:

1. Read the applicable `AGENTS.md`.
2. Understand the feature or correction being implemented.
3. Identify the intended behavior.
4. Inspect the related requirements and acceptance criteria.
5. Identify the affected project area.
6. Understand relevant architectural decisions.

Do not review code without understanding the purpose of the change.

**Deliverable:** Review context.

### Phase 2 — Inspect the Repository and Diff

Inspect the current repository state.

When applicable, execute:

```bash
git status
git branch --show-current
git diff --stat
git diff
git log --oneline -10
```

For Pull Requests, compare the source branch against the correct target branch.

Inspect:

- Added files.
- Modified files.
- Deleted files.
- Changed dependencies.
- Configuration changes.
- Tests.
- Documentation.
- Unexpected modifications.

Consider uncommitted changes when they are part of the requested review.

Do not assume that the working directory is clean.

**Deliverable:** Scope of reviewed changes.

### Phase 3 — Functional Correctness

Verify whether the implementation satisfies the expected behavior.

Check:

- Business rules.
- Conditional logic.
- Data processing.
- Input validation.
- State management.
- API request and response handling.
- Error handling.
- Boundary conditions.
- Missing scenarios.
- Compatibility with existing functionality.

Look for cases where the code works in the normal scenario but fails with invalid, empty or unexpected data.

**Deliverable:** Functional findings.

### Phase 4 — Architecture and Code Quality

Evaluate whether the changes follow the project's architecture.

Check:

- Separation of responsibilities.
- Module organization.
- Reusability.
- Dependency management.
- Naming conventions.
- Code duplication.
- Unnecessary complexity.
- Coupling.
- Maintainability.
- Consistency with existing patterns.

Do not recommend large refactoring solely because another approach is personally preferred.

Prioritize changes that materially improve correctness or maintainability.

**Deliverable:** Architecture and quality findings.

### Phase 5 — Security Review

Inspect security-sensitive changes.

Check applicable areas:

- Authentication.
- Authorization.
- Access control.
- Input validation.
- Output handling.
- Sensitive information exposure.
- Secrets and credentials.
- SQL injection.
- Cross-site scripting (XSS).
- Cross-site request forgery (CSRF).
- Insecure dependencies.
- Unsafe file operations.
- Insecure configurations.
- Logging of confidential information.

Pay particular attention to changes involving user permissions, personal information, external integrations and database operations.

Do not claim that the application is secure merely because no obvious vulnerability was found.

**Deliverable:** Security findings.

### Phase 6 — Performance and Reliability

Evaluate potential problems involving:

- Unnecessary database queries.
- Repeated API requests.
- Inefficient loops.
- Excessive rendering.
- Memory usage.
- Resource leaks.
- Missing pagination.
- Blocking operations.
- Unnecessary dependencies.
- Failure recovery.
- Network and service timeouts.

Only report performance concerns when there is a credible technical reason or supporting evidence.

**Deliverable:** Performance and reliability findings.

### Phase 7 — Tests and Validation

Inspect the tests associated with the changes.

Check:

- Whether relevant behavior is covered.
- Whether new business rules have tests.
- Whether error scenarios are covered.
- Whether bug fixes include regression tests.
- Whether tests are meaningful.
- Whether existing tests remain compatible.

Execute available validations when authorized and possible.

Consider:

- Unit tests.
- Integration tests.
- End-to-end tests.
- Linting.
- Type checking.
- Production build.

Record the commands actually executed and their results.

A code review can identify issues even when tests cannot be executed.

**Deliverable:** Validation evidence.

### Phase 8 — Classify Findings

Use the following severity levels:

- **CRITICAL:** severe security vulnerability, data corruption, major system compromise or critical failure.
- **HIGH:** major functionality broken, serious security issue or significant regression.
- **MEDIUM:** relevant defect that affects a specific scenario or creates a meaningful maintenance or reliability risk.
- **LOW:** limited issue with minor impact.
- **INFO:** suggestion, observation or improvement that is not necessarily a defect.

For every actionable finding, provide:

1. Severity.
2. File and relevant line.
3. Description of the problem.
4. Evidence or reproduction scenario.
5. Impact.
6. Recommended correction.

Do not classify personal preferences as defects.

Avoid speculative findings without a clear explanation.

### Phase 9 — Evaluate Integration Readiness

Based on the evidence, classify the review:

**Approved**

No blocking findings were identified and the reviewed changes satisfy the applicable criteria.

**Approved with Suggestions**

No blocking defects were identified, but optional improvements remain.

**Changes Requested**

One or more relevant problems must be corrected before integration.

**Inconclusive**

The available information or validation was insufficient to establish readiness.

A review must not be marked Approved when a known critical or high-severity problem remains unresolved.

### Phase 10 — Final Review Report

Use the following structure:

#### Review Summary
Brief description of the reviewed changes.

#### Scope
Branches, commits, files or Pull Request evaluated.

#### Findings
List identified problems, ordered by severity.

#### Validation
Commands executed and actual results.

#### Positive Observations
Relevant improvements or correct implementation decisions.

#### Limitations
Missing tests, inaccessible dependencies or unverified scenarios.

#### Recommendation
Approved, Approved with Suggestions, Changes Requested or Inconclusive.

## 4. Special Rules

### Reviewing AI-Generated Code

Pay particular attention to:

- Invented dependencies.
- Incorrect API assumptions.
- Duplicated implementations.
- Unnecessary abstractions.
- Missing error handling.
- Incorrect project conventions.
- Changes outside the requested scope.
- Claims of successful validation without evidence.

### Reviewing Team Contributions

- Do not overwrite another developer's work.
- Respect branch ownership.
- Do not change reviewed code unless explicitly requested.
- Identify potential conflicts with parallel development.
- Preserve the existing Git history.

### Reviewing Without Execution

If tests or the application cannot be executed, perform static analysis where possible.

Clearly state that the review was limited to source inspection.

Never present static analysis as equivalent to executed tests.

## 5. Mandatory Rules

- Never approve code without inspecting the actual changes.
- Never invent defects or test results.
- Never ignore critical security problems.
- Never confuse personal preferences with functional defects.
- Never modify code during a review unless requested.
- Never delete or rewrite another developer's work.
- Never merge or approve a Pull Request without authorization.
- Always provide evidence for actionable findings.
- Always identify limitations.
- Always respect the project's `AGENTS.md`.

## 6. Completion Criteria

A review is complete when:

- The scope has been identified.
- Relevant changes have been inspected.
- Functional correctness has been evaluated.
- Security and architecture have been considered.
- Relevant tests have been inspected or executed.
- Findings have been classified.
- Integration readiness has been reported.
- Limitations have been documented.

## 7. Guiding Principle

A good code review protects the project before problems reach the main branch.

Prioritize correctness, security and maintainability. Every finding must be clear, relevant and supported by evidence.
